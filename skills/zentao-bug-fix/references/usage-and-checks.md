# 调用示例与行为检查

用户可以自然语言覆盖选择条件、数量、验证方式、写回策略和文档目录；无需记参数格式。下面的编号仅是示例，不内置具体项目地址或设备授权。

## 可直接改写的调用

### 多任务快捷入口

```text
使用 $zentao-bug-fix，禅道链接：<粘贴实际链接>。
帮我新建多个独立聊天修复 Bug，最终由主聊天汇总结果 Markdown 文档。
```

用户也可以在支持 Skill 提及的界面选择 `@zentao-bug-fix` 后附链接和“帮我多任务修复 Bug，最终汇总结果 md 文档”。这表示每个 Bug 新建一个侧栏聊天，主聊天负责最终验收和汇总，不是隐藏子代理。是否能用 `@` 选择取决于客户端，纯文本可使用上面的 `$` 形式。

默认选取当前页最多 3 条“激活且未确认”的候选，最多并行 3 个；同文件或依赖冲突的排队处理。验证通过后改为“已确认”，Bug 生命周期保持不变；报告默认名为 `repair-results.md`。普通请求没有“多任务/新建聊天”意图时，不自动开聊天。设备仍需明确授权。

### 指定批量数量和并发

```text
使用 $zentao-bug-fix，从这个列表选 10 条未确认且激活的 Bug，
每个 Bug 新建一个独立聊天，最多同时执行 3 个。
通过最终验收后改为已确认，主聊天汇总成功、失败、受阻、跳过的结果文档。
```

需要主聊天通过消息工具补充任务指令时，可明确补充“允许主聊天向本批创建的任务发送必要协调消息”。没有这项授权也可通过初始任务说明、证据文件和主聊天读取结果完成汇总；不要求子聊天回发消息。

### 处理未确认 Bug

```text
使用 $zentao-bug-fix，从当前禅道项目中选 2 条激活且未确定的 Bug，按当前列表顺序处理。排除当前源码已修复的问题，修复并验证后改为已确认，Bug 状态保持不变。按项目约定生成成功和失败结果文档。
```

### 处理已确认 Bug，修复后标记已解决

```text
使用 $zentao-bug-fix，处理当前项目已确认、仍激活的 3 条 UI Bug。使用现有离屏截图验收；通过后保持已确认，并将 Bug 状态改为已解决。解决版本若无法从本次发布信息查明，先询问我，不填猜测值。生成逐条成功与失败报告。
```

### 指定编号、暂不写回禅道

```text
使用 $zentao-bug-fix，只修复 Bug 12345 和 12346，不限制是否确认，先不修改禅道。使用聚焦测试和静态检查，暂不做视觉或设备验证。报告中列明各条成功、失败及未验证项。
```

### 指定本次设备权限

```text
使用 $zentao-bug-fix，修复 Bug 12345。只在本次任务的荣耀手机复现和验证，允许覆盖安装修复包、启动、点击、截图及采集本次相关日志；不允许卸载、清数据或重置。若有多台荣耀，先让我指定。通过后改为已确认并刷新核验，报告记录安装和实际场景结果。
```

### 两种确认状态都处理，限定数量

```text
使用 $zentao-bug-fix，处理当前项目激活的 2 条 Bug，未确认和已确认的都可以。修复验证通过后设为已确认，Bug 状态保持不变；失败项不要改状态，逐条写入结果文档。
```

### 只分析

```text
使用 $zentao-bug-fix，只分析当前页面 Bug 的根因和验证方案，不改代码、不操作设备、不写回禅道。只输出分析结论，不执行修复流程。
```

## 维护时的代表场景

用下表作桌面推演或经另行授权的实际验收。推演不访问生产禅道、不操作设备，不等同于端到端运行成功；若使用实际 Bug，复用真实工具结果并注明日期与覆盖边界。

| 场景输入/观察 | 应观察到的决策与输出 |
| --- | --- |
| “修未确定的 1 条”，页面有“是否确认”和“Bug 状态” | 映射到未确认，列表默认激活；成功后确认字段为已确认，生命周期保持；报告写两字段 |
| “修已确定、仍激活的 Bug”，源码缺陷仍在 | 不能因已确认跳过；修复验证，确认字段已符合则不重复确认 |
| 指定一个编号，用户明确说已修好但未要求换题 | 该条跳过并给依据，不修改代码/状态，不自动修别的编号 |
| 用户已授权列表继续，第一条源码已有修复 | 记该条跳过，范围内换下一条；不把跳过项当本轮修复成功 |
| 要求只改代码不写禅道，约定验证通过 | 报告代码成功、写回不适用；不执行确认/解决或添加评论 |
| 要求通过后已解决，页面必填解决版本而本次证据缺失 | 定向询问版本，已完成修复仍保留；写回受阻，不编造版本或提交 |
| 未提供设备授权，仅说“修复并验证” | 不探测 ADB；先非设备检查，需要视觉时询问方式 |
| 已授权单台真机验证，但未授权覆盖安装 | 先授权范围内前置检查，确需安装再申请；不使用其他任务权限 |
| 已授权真机和覆盖安装，但正常入口缺外设能力 | 标记场景受阻；不先盲目构建/安装，不改权限或伪造能力；改验收路线需用户选择 |
| 用户改选已有离屏截图 | 继续离屏并保留真机场景未验证边界；新录图不能称为基准比对通过 |
| 必要测试失败 | 记录失败阶段/命令/证据；不把该条标为成功或改确认字段 |
| 修复测试通过，但禅道提交超时 | 先读回；已符合目标则不重复提交；无法判定记待核验，明确成功的代码阶段 |
| 提交弹窗关闭，父页面仍显示旧值 | 刷新核验同一编号及两个字段，不能只凭提示宣称成功 |
| 第二次读取发现他人已将 Bug 关闭 | 不按旧快照覆盖；记录并澄清影响决策的冲突 |
| 一批 4 条分别通过、测试失败、缺权限、已修复跳过 | 文档四类齐全，成功 1/失败 1/待处理 1/跳过 1；各条有阶段、字段和证据 |
| 修复前红测失败、修复后绿测通过 | 红测是复现证据，不计入最终失败 Bug；保留完整命令和结果 |
| 链接加“多任务修复”，未指定数量 | 默认当前页最多 3 条激活且未确认的 Bug，每条创建独立侧栏聊天；总报告记录实际身份 |
| “修复 10 条，并发 3 个” | 冻结 10 条队列，最多 3 个同时执行；同文件/依赖冲突排队，不一次启动 10 个 |
| 仅讨论或修改多任务 Skill，并引用调用示例 | 维护 Skill，不访问禅道、不创建真实修复聊天、不执行示例中的设备操作 |
| 侧栏任务工具不可用 | 如实说明能力缺口，不把隐藏子代理或臆造任务 ID 当作侧栏聊天 |
| 两条 Bug 需要修改同一文件 | 处于不同轮次，前一条编辑结束后才启动后一条；保留用户和其他任务差异 |
| 子聊天完成代码但主验证失败 | 最终报告为失败，禅道保持；不能按子聊天的完成消息计为成功 |
| 子聊天需要 Gradle/截图，同工作区其他任务仍在写代码 | 先收齐本轮编辑，再由主聊天集中验证，不争用 build 目录或共用手机 |
| 创建返回 clientThreadId 或创建超时 | 保留暂态身份，解析正式 threadId 后才读取/等待；重试前检查是否已创建，避免重复 |
| 主聊天未获跨聊天发消息授权 | 用初始完整指令、读取结果和独立证据汇总，不自动调用消息工具 |
| 未确认列表会因确认操作移除记录 | 先冻结编号、按项目加编号去重，再改状态；不在变化中的分页上反复取下一行 |

格式校验只证明文件结构可读。实际浏览器版本、站点字段、设备能力和权限仍须每次从运行环境核实。
