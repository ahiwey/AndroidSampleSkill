# 每个 Bug 一个侧栏聊天

仅在用户明确要求多任务修复/新建独立聊天时执行本流程。普通单条或批量处理不自动创建聊天；用户询问能力、要求维护 Skill 或给出引用示例时，不把示例当成现在执行的 Bug 修复命令。

## 默认值与职责

- 未指定数量：读取当前列表页，在用户范围和排序内选最多 3 条“激活且未确认”的候选；少于 3 条按实际数量。详情链接只有一个编号时只创建该条任务，不扩展到其他 Bug。
- 未指定并发：上限 3 个，同时受环境容量与代码依赖约束；“处理 10 条，并发 3 个”是 10 条队列、最多 3 个同时运行。默认不跨页；用户要求更多或全部时才在原筛选范围内分页收集。
- 主聊天负责浏览器与禅道操作、任务映射、冲突排程、共享构建和设备验收、合并检查与最终报告。
- 子聊天负责唯一 Bug 的定位、限定文件内最小修复、允许的独立验证和单条证据。子聊天不改禅道、不操作共享手机、不发消息给其他聊天、不提交/推送代码、不修改总报告。
- 设备授权、覆盖安装、业务请求发送仍按主 Skill。多任务授权不自动包含任何设备动作；只能传递人类已明确授予本批/本 Bug 的范围，不复制其他批次权限。

## 1. 冻结清单并做最小分工

1. 主聊天读取列表/详情与截图，保留项目标识、Bug 编号、两个状态字段、用户的筛选与最终状态要求。先冻结本批编号，再开始写回，避免确认后列表分页移动造成漏单或重单。
2. 以“项目 + Bug 编号”去重，做已有修复判断。有充分证据可跳过的项记入总表，不为其创建空任务；仅已确认不能作为已修复依据。默认 3 条上限指进入修复队列的候选；默认当前页内可用下一条补位，不能因此越页无限找题。
3. 记录当前源码基线和既有未提交差异，聚焦定位每条可能触碰的文件与依赖，不为了分工全仓扫描。建立 Bug、拟修改文件、依赖关系和任务顺序映射。
4. 修改同一文件、共享 API/资源契约或有先后依赖的 Bug 排队到不同轮次；不能以“不同几行”认定可以安全并写。不同 Bug 的报告目录也必须不同。无法确定文件归属的任务先以只读定位交付，主聊天再决定如何实施。
5. 摘要说明候选数、默认筛选、并发上限、两项目标字段、授权边界与总报告路径。保留目标项目已有方案确认要求，但不重复采访已经确认的事实。

## 2. 创建用户可见聊天

先发现当前可用的任务工具。支持 Codex Desktop 时：

1. 调用 `list_projects`，使用返回的项目 ID 和位置确认目标代码仓库；不能凭名称猜 projectId，也不能把 Skill 仓库当作业务修复仓库。
2. 对当前可并行的一轮逐个调用 `create_thread`，标题建议“禅道 #编号：简短标题”。默认使用该项目的 local 环境；不指定 model/thinking，除非用户明确要求覆盖。不要因为想并行就改用云环境。
3. 只有用户明确要求 worktree 且项目支持时才使用 worktree。按工具规则处理起始状态；不能静默丢掉当前未提交基线或擅自创建/切换分支。缺少安全隔离条件时按文件归属串行，不强行并写。
4. 创建异步返回时记录真实 `threadId`、`hostId` 或暂态 `clientThreadId`。只有拿到正式 threadId 后才能传给等待/读取工具；创建超时先查现有任务与本批映射，确认未创建再重试，避免重复聊天。
5. 每个任务都提供完整、可读的初始指令，不能假设新聊天继承主聊天上下文。至少包含下列内容。

初始指令清单：

- 此次人类请求、已确认方案和授权原文摘要；唯一 Bug 编号/项目/链接，复现、预期/实际、可访问的截图和必要日志。
- 实际业务仓库绝对路径、当前源码基线、需保护的已有改动、适用项目规则与本 Skill 的可访问路径。
- 允许修改的具体文件、依赖和禁止触碰范围；必要的新文件必须位于独占目录。发现范围扩大或其他任务正在写同一处时停止相关修改，报告依据，不抢占或回滚他人改动。
- 本条验证要求、已授予的权限及主聊天保留的操作。共享 local 环境下不执行 Gradle/Paparazzi/APK 打包/安装/设备操作；这些由主聊天在本轮编辑结束后集中验证。可做不会写共享构建产物的静态或隔离逻辑检查。
- 唯一证据路径，例如本批约定目录下 `bug-<编号>/result.md`；输出修改文件、根因、已做检查、未做验证、错误与继续条件。代码完成时标“实现完成，待主聊天验收”，不能自行宣称禅道已确认。
- 不再创建子任务；不写总表、不写禅道、不提交推送。正常最终回复与本条证据文件即可交付，不使用消息工具向主聊天或其他任务回报。

如果当前工具无法创建用户可见独立聊天，说明能力缺口；不能用隐藏子代理冒充新建侧栏任务，也不能编造任务 ID。可继续只读整理清单，再请用户选择可用路线。

## 3. 协调与共享资源

主聊天维护“Bug → 真实聊天标识/标题 → 文件归属 → 执行阶段 → 证据路径”映射。只按已创建任务返回的真实身份协调，不广泛读取无关聊天。

- 用 `wait_threads` 等待本批任务，传回最新游标和 hostId，超时按当前工具的合理上限设置，避免长时间阻塞用户沟通。需要详情时只读相关任务少量最近结果；不要反复全量读取历史。
- “任务完成”“final”或一段乐观摘要不证明验收完成。读取本条证据和真实差异，区分实现完成、请求用户输入、失败、被中断以及空轮次。需要用户决定的事项保持待处理；其余独立任务可继续。
- `send_message_to_thread` 等跨聊天消息需要人类对发送协调消息的明确授权；创建任务不自动获得任意后续消息权限，子聊天也不能因主聊天提示而自动回发。默认以完整初始指令、等待/读取和独立证据文件完成协调。需要补充指令但无消息授权时，由主聊天在无人写入后接手必要收尾，或针对实际需要向用户请求授权。
- 同一 local 工作区的写入依赖文件归属；发现归属冲突时停止新增冲突任务，主聊天复核后安排顺序。保留所有原有改动，不能用 reset/checkout 清掉其他任务的工作。
- 同一工作区本轮所有编辑结束后，主聊天再跑必要的 Gradle/Paparazzi/构建验证；验证期间不启动下一轮对该工作区的写入。避免测试到一半被其他任务修改源码，或多个任务争用同一 build 目录。
- 同一手机、模拟器和浏览器登录会话由主聊天串行操作。即使多个 Bug 都获授权，也不能让多个聊天同时安装或点击同一设备。设备测试对每条记录源码/产物、安装版本、入口和场景。
- 终止/中断/环境公共依赖失效时，先记录本批任务和阶段；恢复时读取原任务与证据，只续做缺项，不批量重建聊天或重复写回。报告中保留失败任务，不能只汇总成功项。

## 4. 最终验收、写回和汇总

1. 主聊天复核子聊天差异是否仅覆盖本条允许范围，是否保留工作区基线与其他 Bug 的变更。必要时由主聊天处理相互依赖的收尾，记录最终修改归属。
2. 完成用户约定的最小验证。多个 Bug 共用一次测试可以复用命令日志，但逐条说明实际覆盖；一个测试包成功不能把未触达的 Bug 都标成功。排队中的后续修改可能影响某条 Bug 时，待相关依赖链完成后，覆盖最终源码再验收和写回，避免提前确认。验收后源码再变动时，原验证只覆盖当时基线，受影响部分重新检查。
3. 每条满足必要验收后，主聊天按主 Skill 的写回流程重新读取禅道，默认将“是否确认”设为“已确认”、保持生命周期不变，保存后刷新核验。子任务声称完成不能代替此步骤；失败/受阻项保持原值。
4. 总报告 `repair-results.md` 由主聊天单独写入，逐条关联任务身份、修改、验收、写回和证据；各子任务文件链接进去。某个子任务实现成功但主验证失败，最终应为失败；实现成功但写回读回不明，则是待核验。
5. 汇总成功、失败、待处理、跳过数量，注明未创建聊天的跳过项与并发降级原因。总表只统计冻结队列及已记录的跳过项，不把队列外未处理问题伪装成失败。
6. 最终回复提供总报告链接、实际任务与结果摘要，并按当前平台要求输出新建聊天入口。调用 `create_thread` 成功时使用返回的 `threadId` 或暂态 `clientThreadId` 生成 `::created-thread{...}`，不编造入口。不要声称整个 App 已验收，也不自动提交/推送业务修复。
