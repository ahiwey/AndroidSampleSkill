# 代表案例

用于维护时的有界行为复核；输入中的库名/类名为场景而非必加规则。主代理阅读推演不是独立盲测；需要产物断言时使用已授权的既有样本，不自动构建或连接设备。

| 输入证据 | 应有决策/验收 | 不应出现 |
| --- | --- | --- |
| 普通功能新增本地缓存，外层 codegen、内层枚举走 Moshi 默认 adapter | 无需专项请求即触发局部检查，追枚举注解/consumer及成员，检查旧缓存值 | 外层生成代码即全链路安全、只看网络 DTO |
| Gson 字段有 SerializedName，但模型只通过泛型反序列化实例化 | 检查承载类、构造/实例化和泛型，不只保字段；需要时查实际 DEX | 注解存在或 Debug 测试通过即判 Release 安全 |
| 新类仅承载 UI 状态，无 JSON/反射消费者 | 记录不需要额外注解/keep的依据，结束局部检查 | 给所有 data class 加 JsonClass/Keep，启动全应用审计 |
| 使用已注册且实际选中的自定义枚举 adapter | 按真实读写契约和动态用途判定，不套默认反射方案 | 所有枚举一律加同一种注解 |
| Release 登录错误，响应业务码/解析形状异常，无混淆证据 | 沿异常栈与实际响应定位，保留原因未定边界 | 仅因 Release 出错就加 keep |
| 旧版 JSON 库 JAR 没有 consumer；模型字段无注解；历史缓存需读取 | 保护实际动态创建与字段契约；检查最终字段/构造与旧数据读取 | 按库名认定全部规则冗余、只保新写入数据 |
| 自定义对象使用 ofFloat(obj, "progress", ...)，移除记录包含 setter | 检查并定向保留所需 getter/setter；检查 DEX 和实际动画 | 仅确认类存在、整包保留、把平台 View 的规则当覆盖 |
| SDK consumer 有全局 ignorewarnings/重打包/输出路径 | 追溯来源和意图，核实过滤 API/标识，补回 SDK 必要规则，再查合并结果 | 直接删除整份 consumer、升级 AGP 求支持 |
| library 出现在 settings，但目标应用无依赖 | 不把它的 consumer 当作本包有效规则 | 修改未进入应用的规则后宣称已保护 |
| 构建成功但设备只有旧包；同版本号覆盖包哈希不同 | 分开报告构建/安装，确认最终产物安装及进程 | 以版本号相同或 debug 启动当 release 已验证 |
| App 有缓存设备名，录音列表为空 | 仅报告已显示页面，JNI 解码/外设同步未验证 | 宣称 BLE/JNI 全流程通过 |
| 新包恢复规则后仍出现列表别名自清空 | 用源码/运行证据归类业务缺陷，按授权单独修复 | 继续加 keep 或宣称优化导致一切异常 |
| 用户仅要求分析，没有设备授权 | 定向读取现有文件/产物，输出建议与未验证项 | 新建未知位置报告、启动构建/ADB/自动安装工具 |
| 只有不同 ABI 的 Debug 与 Release 体积 | 说明缺少可比基线 | 给出准确优化百分比或启动性能提升 |
| 已授权修复和本任务真机验证，中途继续 | 复核变更，续做缺项，不重复确认 | 把既有授权作废或继承其他任务设备授权 |
